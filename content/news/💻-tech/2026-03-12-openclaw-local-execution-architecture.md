## 핵심 요약
- OpenClaw는 <strong>클라우드 중심 AI</strong> 흐름과 달리, 사용자 PC에서 직접 동작하는 <strong>로컬 우선 실행형 에이전트</strong>를 지향해.
- 게이트웨이(컨트롤 플레인) 중심의 <strong>hub-and-spoke</strong> 구조 + WebSocket 기반 실시간 통신으로 채널·세션·상태를 묶어 운영해.
- “답변 생성”이 아니라 <strong>도구(tool) + 스킬(skill)</strong>을 통해 파일·브라우저·쉘·메시징까지 실제 행동을 수행하는 모델을 제시해.

## 주요 내용
요즘 AI 에이전트는 단순 Q&A를 넘어, 실제로 시스템을 조작하고 작업을 수행하는 “실행 주체”로 진화 중이야. 그런데 대부분의 AI 서비스는 여전히 클라우드 중심이라, 데이터가 외부 서버로 나가고(또는 나갈 가능성이 생기고), 모델 실행도 원격에 의존해. 이 글이 흥미로운 지점은 OpenClaw가 그 반대 방향—즉 <strong>로컬 우선(Local-first)</strong>—을 선택했다는 점이야.

OpenClaw는 “챗봇”보다 “사용자의 컴퓨터와 디지털 환경을 이해하고 행동하는 AI 시스템”에 가깝게 정의돼. 핵심 철학은 크게 3가지로 정리돼:

1) <strong>로컬 실행</strong>: API 기반 상용 LLM을 붙이지 않는 한, 기본적으로 로컬에서 처리되어 데이터 외부 유출 표면을 줄이는 구조
2) <strong>확장 가능한 아키텍처</strong>: 다양한 채널(텔레그램/디스코드/슬랙 등)과 도구를 연결해, “채팅 앱 = 제어 콘솔”로 활용
3) <strong>일상 자동화 중심</strong>: 엔터프라이즈 SaaS가 아니라 개인의 반복 작업을 줄이는 데 초점을 둔 실행 모델

아키텍처 관점에서 OpenClaw의 중심은 <strong>게이트웨이</strong>야. 이 게이트웨이는 컨트롤 플레인으로서 메시지 라우팅, 세션/상태 관리, 채널 연결 유지 같은 “허브” 역할을 하고, 실제 상호작용은 <strong>WebSocket</strong> 기반으로 지속적인 이벤트(도구 호출/스트리밍/상태 업데이트)를 처리해. 전통적인 HTTP 요청-응답보다 “항상 연결된 작업 흐름”에 적합한 방식이지.

또 하나 중요한 축은 <strong>Agent</strong>와 <strong>Agent Runner</strong>의 분리야. 에이전트는 워크스페이스·히스토리·정책·모델 설정처럼 ‘기억과 성격’을 정의하는 논리 단위이고, 러너는 실제 모델 실행과 도구 호출을 담당해. 이 분리는 운영/보안/확장 측면에서 꽤 유리해져(정책은 정책대로, 실행은 실행대로).

마지막으로 OpenClaw를 “실행형 AI”로 만드는 건 <strong>도구(tool)</strong>와 <strong>스킬(skill)</strong> 구조야. 도구는 브라우저 자동화, 파일 읽기/쓰기, 쉘 실행 같은 개별 실행 인터페이스고, 스킬은 여러 도구 호출을 묶어서 목적 중심의 “완결된 행동 단위”로 만든 템플릿이야. 즉 AI가 글을 ‘잘 쓰는 것’에서 멈추지 않고, 실제로 정리하고, 클릭하고, 실행하고, 전송하는 쪽으로 확장될 수 있는 기반을 제공해.

## 결론 / 인사이트
OpenClaw 사례가 던지는 메시지는 단순해: 앞으로는 “클라우드에 답을 물어보는 AI”보다, <strong>내 환경에서 안전하게 행동하는 로컬 실행형 에이전트</strong>가 더 중요해질 수 있어. 다만 강력한 실행 권한은 곧 공격 표면을 넓힌다는 뜻이기도 해서, 최소 권한/승인 기반 실행/프롬프트 오염 방어 같은 단말기 중심 보안 설계가 같이 가야 해.
